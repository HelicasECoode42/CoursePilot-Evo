# 学生究竟在意什么：选课需求研究与单问题页面规范

日期：2026-09-30。状态：公开资料研究、产品设计与 HTML 交互原型；不是已上线功能，也不是本校学生调查结果。

## 1. 这次调整的产品结论

CoursePilot 应帮助学生在一处完成“看自己的学业进度、了解课程和教师、表达偏好、比较方案”。职业发展只是其中一种选课动机。高绩点、少签到、低工作量、好评教师、兴趣和特定教师课程都应当被独立表达，允许同时存在。

前端一次呈现一个问题，回答后替换为下一页。学生界面只显示决策所需信息。架构、Java、System 1/2、Harness、Benchmark、工具契约均放在开发文档里。复杂度留在系统内部，不让学生读项目说明才能选课。

已修课、专业、年级、培养方案路径来自已接入的学业记录；正常流程只让学生检查、纠错和补充缺失项。首次没有记录时，才给“导入记录”的入口。不能要求每次手填所有已修课程。

本学期必修课的候选清单由教学计划、已修记录、先修规则与真实开课快照联合计算。教学计划中的建议学期不等于“本学期必须修”，也不保证本学期开课。界面区分“尚未完成的必修要求”“建议本学期修读”“本学期可选班次”，并说明证据；无法确定的部分提示待核对。

## 2. 研究证据与边界

公开研究《大学生选课动机及在线学习行为机制研究》的检索摘要涉及个人兴趣与能力、课程性质和挂科风险、教师教学以及他人影响。这支持把需求拆为多个维度；本次工具未能读取 PDF 正文，不能据此引用样本比例或推断本校排序。[论文入口](https://xb.cyu.edu.cn/zxqk/gqml/202304/W020230413614320107375.pdf)

南开课程经验社区鼓励分享课程内容、作业量和难度、课堂感受，并要求用具体任务说明支撑评价。这提示我们保留可核查的作业频率、任务类型，而不是只展示“很水”标签。[南开课程经验分享](https://nkucs.icu/)

USTC 评课社区可以看到同一课程、不同教师以及不同修读年份的评价；个别评价讨论作业、评分规则、出勤和汇报体验。这说明课程名称不能单独充当评价对象，评价必须关联教师与学期。个体评价不能代表全体学生。[USTC 社区](https://www.icourse.club/)、[一则课程评价页面](https://www.icourse.club/course/26594/?sort_by=score)

交大课程社区的官方前端仓库展示课程评价产品的实现背景；交大 courses-icu 项目强调课程概览、学习指导和未来路线的信息共享。这些是产品参考，不是已经获得的数据源授权。[课程社区前端](https://github.com/SJTU-jCourse/jcourse_vite)、[课程信息共享项目](https://github.com/SJTU-CSE/courses-icu/blob/master/README.md)

GOV.UK 的 question-pages 模式支持从“一页处理一件事”出发设计表单。本项目据此采用短页面、返回后保留答案、条件追问；它不是要求所有学生走固定长问卷。[Question pages](https://design-system.service.gov.uk/patterns/question-pages/)

用户提供的 https://course-rate.icu/ 本次网页读取失败，未验证其字段、评价数量、接口、覆盖范围、授权与更新时间。仍是待核查的本校评价入口，不能把其他学校的评价移植为本校数据，也不能伪造该站评价。五周原型可以用自建、明确标为演示的评价 fixture，正式接入另做字段和使用范围确认。

以下需求矩阵是“用户反馈 + 公开资料 + 产品推导”的候选集合，不声称每项都有统计证据。第一周应请本组或同学用真实选课经历复核，重点记录哪些维度重要、哪些根本不关心。

## 3. 学生可能在意的完整需求矩阵

| 维度 | 学生可能怎么说 | 要查什么 | 页面如何表达 | 不可承诺的内容 |
| --- | --- | --- | --- | --- |
| 毕业进度 | 我到底还差什么？ | 培养路径、类别学分、已修和替代规则 | 自动给出缺口与可满足要求的课程 | 没有完整记录时算出确定缺口 |
| 必修与先修 | 这门现在不上会不会耽误后面的课？ | 先修、建议学期、后续课程、开课历史 | 展示顺序建议及依据 | 计划建议就是行政硬要求 |
| 高绩点 | 想选相对容易拿高分的 | 同教师同课历年给分反馈、考核方式、样本年份 | “给分反馈”与样本说明，可比较 | 保证高分、捏造均分或成绩分布 |
| 保过与重修 | 不想再挂，想补过这门 | 先修基础、考核难度、已有失败记录 | 低风险候选、基础补齐提醒 | 必过、难度对每个人相同 |
| 少签到 | 我想要不点名、少签到的老师 | 课程大纲中的考勤要求、近期学生反馈 | 独立的签到偏好与证据 | 历年没签到等于本学期不签到 |
| 低作业量 | 这学期实习，想轻松一点 | 周作业、实验、报告、项目等 | 工作量类型与频率，不只总分 | 给没有来源的每周小时数 |
| 考核形式 | 不喜欢闭卷，想做项目 | 闭卷/开卷/报告/项目、权重 | 明确的考核形式筛选 | 用往年形式保证本学期相同 |
| 小组作业 | 不想被队友拖累 | 是否组队、人数、分工、评分方式 | 小组任务单独显示 | 无评价就认定没有组队 |
| 展示与讨论 | 不想做 pre，或想练表达 | 汇报、课堂发言、讨论占比 | 接受/避开/无所谓 | 把少作业误判为少展示 |
| 给分公平 | 我在意标准清楚、反馈认真 | 大纲评分规则、具体评价证据 | 评分透明度反馈，保留分歧 | 将个别负面评价写成教师定论 |
| 教师授课 | 我想要讲得清楚的老师 | 讲解、节奏、答疑、课程组织 | 课程×教师的授课反馈 | 用热度代替教学质量 |
| 指定教师 | 我就想上某老师这门课 | courseId、teacherId、offeringId | 搜索课程和教师，锁定具体组合 | 只锁课程就替换成别的老师 |
| 指定课程 | 特别想学这门，老师可以换 | 同课程各教师各班次 | 分清课程锁定与教师锁定 | 静默换成名字近似的另一门课 |
| 回避教师或班次 | 这位老师/这个班我不想选 | 学生明确表达的回避清单 | 可编辑回避项，无需让学生证明理由 | 从一次聊天推导永久教师黑名单 |
| 好评课程 | 只想看看大家评价好的 | 评价维度、条数、时间、矛盾意见 | 可选“总体体验优先”，能展开原文 | 两条好评就宣称全校认可 |
| 真正学知识 | 想学扎实，难一点也行 | 内容、教学大纲、实验、先修匹配 | 内容与训练方式优先 | 好评、轻松、高分是同一属性 |
| 职业技能 | 想往某种工作准备 | 岗位任务、技能与课程内容映射 | 先看方向介绍，再选课程 | 修一门课就具备岗位能力 |
| 升学科研 | 想考研/保研/做科研 | 学生目标、基础课、项目训练、官方要求 | 与绩点和工作量分别建目标 | 虚构招生、保研或实验室要求 |
| 兴趣探索 | 只是想试试看，不想定职业 | 主题、难度、先修、实际内容 | 允许轻量探索与不确定 | 强迫选择终身职业标签 |
| 学分效率 | 想尽快补够某一类学分 | 学分、类别归属、重复计入规则 | 精确核算有效学分 | 多学分一定划算或可重复计入 |
| 时间底线 | 周五要实习，不能排课 | 每个班的周次、星期、节次 | 单独确认“必须”还是“尽量” | AI 自行猜上课时间 |
| 时间偏好 | 不要早八，想少空堂 | 时段、空堂、连续节数 | 偏好比较与取舍 | 牺牲硬条件提高软分 |
| 校区与通勤 | 两个校区赶不过去 | 校区、教室、上下课时间、可用通勤规则 | 通勤风险另列，不等同节次冲突 | 没有通勤数据时判断一定赶得上 |
| 实习和考试安排 | 想留出准备时间 | 学生明确输入的固定事项、可用考试安排 | 把固定事项当时间约束 | 没有考试时间却保证考试不撞 |
| 容量与成功率 | 我想要有机会选上的 | 当前容量、余量或排名快照及时间 | 数据新鲜度、备选班次 | 静态容量变成实时录取概率 |
| 学伴与社交 | 想和朋友一起上 | 经用户选择的共同课程/时间 | 首版作为手动偏好 | 收集或推断朋友的隐私记录 |
| 资料与资源 | 希望资料全、方便复习 | 教师公开资料、课程资源、来源 | 在课程详情统一入口 | 传播未授权课程材料 |
| 可解释与可修改 | 为什么推荐？换老师会怎样？ | 满足条件、冲突、来源、取舍 | 显示两三个具体理由并支持改条件 | 给一个无法追溯的“AI 最优分” |

这些维度允许独立组合。例：“高绩点 + 不签到 + 周五不能上课 + 想上指定教师”不是四个互斥画像，而是一份任务中的四项要求。系统需要确认每项的优先级和可让步程度。

## 5. 单问题页面及条件分支

默认主线：本学期最在意什么 → 对应目标追问 → 有没有特别想上的课程/教师 → 哪些时间不能上课 → 必要的取舍确认 → 候选方案。

每页只处理一个决策，标题就是问题；选项简短，必要说明一句即可。页面返回保留答案，不展示全部问卷，不要求回答无关职业题。问题页桌面约一屏；手机允许当前问题自身滚动，不能把后续问题接在下面。

第一问提供：高绩点、少签到/轻松些、评价好的课、指定教师课程、兴趣探索、职业准备、升学基础、时间合适。多选且记录选择顺序。后续确认“最在意哪项”，不能以选择顺序永久推断硬条件。

条件追问举例：

- 高绩点：更看重给分反馈还是低挂科风险？能否接受较多作业？不要求学生预测自己的成绩。
- 轻松些：具体是少签到、少作业、少小组任务、少汇报、避开闭卷，还是总投入少？这些不可互相替代。
- 好评课：讲得清楚、评分公平、答疑认真还是整体体验？先展示来源再让学生选。
- 兴趣：想探索的主题和已有基础，不强迫填岗位。
- 职业：按已知专业提供方向介绍，允许跨学科、搜索和“还不确定”。
- 指定教师：选择课程×教师，确认是“必须保留”还是“优先考虑”；缺少开课数据时只能先保存意愿。
- 时间：选出不可上课时段，另问哪些只是尽量避开。不要把“周五最好空”默认为硬约束。
- 取舍：只有真的出现不可满足组合才追问，例如指定教师与周五禁排冲突；不得静默改老师。

岗位介绍、评价原文和学业明细以抽屉/详情页呈现。当前问题仍保留，关闭后无需重填。结果页可比较多个候选班次，而不是把所有工程解释重新堆进页面。

## 7. 每门课、每位教师、每个班次分别展示

课程是学什么；教师是由谁教；班次是本学期什么时候、在哪里上。三个对象不可混为一谈。推荐结果应落实到具体班次，但评价证据主要关联“课程×教师×修读学期”，不能因为课名相同而混用所有教师评价。

候选班次的首层只放：课程、教师、学分/类别（已有依据时）、时间状态、与本次目标相关的 2–3 项评价信息、推荐/不满足理由。选择“看教师与课程详情”后显示：

- 大纲中的内容、先修与正式考核方式；
- 给分反馈、签到反馈、作业/实验/小组/pre 工作量；
- 讲解与答疑反馈、总体体验；
- 来源、修读学期、发布日期、样本条数以及不同意见；
- 原文入口与摘录对应关系；
- 同一课程其他教师班次的比较；
- “特别想上”“必须保留”“备选”“不考虑”四种动作。

评价不是统一五星分。每个维度可以是 UNKNOWN、有限反馈、较一致反馈、存在分歧；可先做结构化标签和有证据的摘要，不必在五周内做复杂统计。

例：“两则往年评价提到未点名，本学期要求未确认”优于“这老师不签到”。“有评价反映给分较友好”优于“选这个保证 4.0”。界面允许学生表达“想找不签到、好混的课”，系统用签到要求和工作量证据作匹配，不凭空保证轻松。

## 8. SQL、检索与 Agent 各自提供什么

新增逻辑对象（详细 API 冻结后接入共享契约，不另造平行 DTO）：

- StudentAcademicRecord：已修记录、通过/重修状态、培养路径及记录完整性。
- AcademicAudit：缺口、未完成要求、建议修读课及每条依据。
- Course、Teacher、Offering、Meeting：课程、教师、学期班次与结构化时间。
- ReviewEvidence：courseId、teacherId、termId、维度、内容、sourceUrl/sourceDocRef、原文定位、时间、来源类型；标明 official 或 student_report，不能混用。
- ReviewSummary：各维度摘要、对应 evidenceIds、样本数、时间范围、分歧和未知状态。数字只来自现有记录统计。
- CareerDirection：专业标签、典型任务、能力主题、课程映射与证据、sourceDate。
- PlanningIntent：motives、明确的优先级、hardConstraints、softPreferences、pinnedCourseIds、pinnedTeacherCoursePairs、avoidItems、unknownFields。

SQL 保存对象、关联和版本，是课程身份、班次、学分、规则和时间的查询入口。评价原文和大纲可以做全文或向量检索，但检索后必须回到正确课程/教师/学期，并返回证据 ID。首版评价数量少时，SQL 条件过滤加文本查询足够；是否加入向量 RAG 由检索规模决定。

Agent 读取学业核对摘要、可选课程和有来源的评价，而不是把整个数据库塞入 Prompt。它澄清意图、组合候选和解释取舍。不得生成不存在的 teacherId/offeringId，不得将社区文字当作确定性时间数据。

正式课表要通过 Java 校验。UNPARSED、UNKNOWN、学期不一致、来源未验证均阻断“无冲突”结论。即使满足时间要求，评价、余量和教务实时调整仍需显示时效。当前示范只有占位数据和用户操作状态，没有真实成绩导入、AI 规划、评价接入或 Java 核验。

## 9. Harness 演化必须覆盖这些真实失败

继续使用四个既定 Task Group，不扩成另一个工作流：

1. 培养要求核对：已修记录不完整时不能编造缺口；区分建议学期与硬要求。
2. hard/soft 理解：正确理解“周五最好空”“不签到优先”“指定教师必须保留”，支持多目标组合。
3. 规划和 replan：指定教师撞硬条件时澄清，不能偷偷换老师；比较同课程不同教师。
4. 缺失信息：评价缺失、单条往年评价、真实班次不可得时承认未知，不生成评分和时间。

失败假设必须跨多个 Trace，例如“Agent 常把少签到视为低工作量”或“它只按课程名检索，混用了教师评价”。Evolver 可修改目标澄清 Skill、评价查询 Tool Policy、上下文中证据的新鲜度规则；Java API、模型配置、评分器与 held-out 隔离规则保持既定约束。

每次测查目标解析、指定对象保留、证据匹配、未知事实拒绝编造、硬约束违规以及 token/tool calls。省 token 必须与 held-out 不退化一起报告，不能靠删掉评价证据和追问获得虚假效率。

## 10. 五周范围与成员衔接

A：已有记录/计划导入和班次规范化；提供完整性和版本状态。评价输入首版支持手动导入，不要求爬取不可访问网站。

B：AcademicAudit、课程/教师/班次查询、先修和冲突核验；“建议”与“硬要求”分别返回。评价内容不由规则引擎认证为客观真值。

C：条件问题路由、结构化意图、指定教师绑定、证据查询与候选解释；生产 Runner 与评测 Runner 共用。

D：加入多动机、教师混淆、评价陈旧、建议学期误判等 case；跨 Trace failure mining 和多轮 gate 按既定方案执行。

E：一次一问、学业记录抽屉、按学科的方向详情、课程教师比较、结果可修改。当前 HTML 用明确占位展示这些流程，不展示工程术语。

五周首版：一个培养路径、少量课程与教师评价样例、统一导入和来源、核心条件问题、指定教师、候选比较、UNKNOWN 阻断。多专业方向只做可扩展内容模型；实时岗位同步、全校爬取、成绩预测、复杂社交与真实抢课成功率留后续。

## 11. 网页技能与设计选择

已搜索并读取官方技能：

- [Anthropic frontend-design](https://github.com/anthropics/skills/blob/main/skills/frontend-design/SKILL.md)：用于本次重设计，要求围绕实际产品作视觉选择、减少装饰与解释、用学生能懂的词。采用白底、少量深绿色、单列主问题、充足留白，强调可点选的答案。
- [Vercel web-design-guidelines](https://github.com/vercel-labs/agent-skills/blob/main/skills/web-design-guidelines/SKILL.md)：用于交互检查。关注键盘、焦点、表单标签、返回状态、小屏布局和详情层。[官方规范](https://vercel.com/design/guidelines)
- 发现方法：[skills.sh](https://skills.sh/) 与本机 find-skills 技能。此次从官方原文读取指导，没有全局安装技能。目录页的累计安装/仓库星数会变化，不能以此保证设计质量。现有 ark-ui 是特定游戏视觉技能，未用于此学生界面。

## 12. 原型验收

- 打开即见一个短问题，不需要滚过项目介绍；下一页替换当前问题。
- 选高绩点/轻松/好评等目标时可跳过职业问题；选择职业时能看专业对应方向介绍。
- 学业背景从记录入口查看，只补充缺失项；必修候选由系统提供。
- 可以同时保留多目标、指定课程教师和排课硬条件，返回不丢答案。
- 每个候选均有教师、评价状态和详情入口；无评价不会出现假分数。
- 真实班次未验证时显示“时间待确认”，不显示真实课表已无冲突。
- 用户页面不出现 Java/Harness/Benchmark/系统分层等开发说明。
- 所有演示学业记录、课程、教师与评价均明确为示例，没有真实数据接入承诺。
