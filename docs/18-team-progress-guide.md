# 团队操作说明：任务、看板、PR 与 Bug

进度入口：[CoursePilot 开发与验收](https://github.com/users/HelicasECoode42/projects/1)。首期任务和后续目标见[排期草案](19-delivery-plan.md)。当前以课程第五至第八周作为排期单位，只维护「周次」，不另设截止日期。学校周次不按 GitHub 的自然周自动推算。

## 1. 三个入口分别做什么

- Issue：一项任务或一个 Bug，记录范围、验收条件、依赖和讨论。
- Project：同一批任务的「任务总表」和「本周进度」视图；不复制另一份进度表。
- PR：代码交付、检查证据和正式复核结论。看板里的计划复核人不等于已经发出 PR 审查请求。

草案任务须由队长与成员核对后，才转为正式 Issue 并分配 GitHub 账号。公开记录仅使用 GitHub 账号，不写姓名和邮箱。已确认：数据 JiangYiLin-Q121、Agent goat-yang、评测 amorfatiii、Web/队长 HelicasECoode42；Java mira-xu。下文 A/B/C/D/E 仅是仓库既有模块编号。

## 2. 看板字段

| 字段 | 规则 |
| --- | --- |
| Title | 可验收结果，不写「完成全部后端」 |
| Assignees | 一名主要负责人；草案阶段可以留空，不猜账号 |
| Status | 待排期、待开发、开发中、待验收、完成、取消 |
| 模块 | 数据、Java、Agent、评测、Web、集成 |
| 优先级 | P0 紧急阻塞；P1 核心交付；P2 可后排 |
| 周次 | 第五周、第六周、第七周、第八周、待排期 |
| 计划复核人 | JiangYiLin-Q121、goat-yang、amorfatiii、HelicasECoode42、mira-xu；多人协作在正文补充 |
| Linked pull requests | 关联代码交付；正式审批状态到 PR 查看 |
| Labels | bug、blocked 等；不再用标签重复维护周次和优先级 |

P0 用于主流程中断、错误核验、数据泄露或全组关键依赖被阻塞。首版必需功能通常是 P1。周次决定哪周做，优先级决定先做什么。

「本周进度」按周次筛选、按 Status 分列。每周队长把筛选切到本期；改筛选后保存视图。任务仍留在同一 Project，不另建每周项目。取消项不计入完成，可从日常视图隐藏或归档。

## 3. 领任务并开始开发

1. 在仓库 Issues 新建「开发任务」，或领取队长发布的 Issue；加入上述 Project。
2. 填负责人、周次、模块、优先级和计划复核人。正文写输入输出、契约链接、依赖 Issue、验收条件。
3. 开工前让接口提供方/消费方核对样例。改变公共接口必须同步 contracts、样例和相关 TRD。
4. 同步 main 后建立自己的短分支，例如 feat/b-audit；不要直接在 main 上提交。
5. 开始后将任务移到「开发中」。每人同时推进一个主要任务；卡住半天就在 Issue 说明阻塞原因、等待谁、已尝试什么，并加 blocked 标签。
6. 工作日有实质变化时更新评论：已完成和证据、下一步、阻塞。进度以可运行结果衡量，不填主观百分比。

## 4. 提交 PR 和复核

1. 先运行仓库检查和受影响模块检查，做 AI 代码审查，处理有效问题。可以使用 requesting-code-review 等技能；不同 Agent 均须读取 Issue、公共契约、模块 TRD 和工程规范。AI 意见由作者核实。
2. 提交小范围 PR，使用模板写清改动、检查命令/结果、未完成项；界面变更附桌面/窄屏和交互证据。审查后新增代码须补查受影响部分。
3. 在 PR 正文写 `Refs #任务编号`，或在 Development 中关联 Issue。本项目初始采用人工验收关单；尚未完成全部验收时不要写自动关单关键词。
4. 在 PR 右侧 Reviewers 请求关联队友审查；按团队约定请队长确认跨模块影响。将 Issue 移到「待验收」。
5. 关联人用约定样例实际调用/运行，检查正常、失败、UNKNOWN 和兼容性。PR 中提交 Approve 或 Request changes；Comment 只是留言，不代表批准。
6. 要求修改时回到「开发中」，修复后重新请求审查。最终代码版本须有适用检查与审查证据。
7. 队长确认验收条件满足、相关审批和 CI 通过后合并。负责人补充合并链接与验收证据，再关闭 Issue 为 completed、看板移到「完成」。跨多个 PR 的任务不能在第一个 PR 合并时提前完成。

作者不能替自己作最终复核；队长自己的 PR 也由队友复核。接口修改至少由一个实际消费者复核。分支保护是否强制审批以仓库设置为准，文档约定不等于已经启用。

## 5. Bug 如何登记和提醒

1. 先搜索有没有同一问题。有则补充复现，不重复开单。
2. 使用「Bug 报告」模板：写最小复现、预期/实际、版本和环境、影响、脱敏证据。疑似问题明确标待复现。
3. 使用 bug 标签并加入同一 Project。队长确认优先级和所属模块，在 Assignees 指定修复人，并在 Issue 中 @实际账号提醒；不把提醒只留在群里。
4. 卡住其他任务时，双方 Issue 互相链接，加 blocked 标签；问题解决后移除标签。
5. 修复 PR 关联 Bug，补能先失败再通过的回归检查。报告者或关联队友复测，合并且复测通过后再关单；复发则重新打开并附新证据。
6. 误报/重复/不做的任务写清原因，以 not planned/duplicate 等适当原因关闭，Project 设为「取消」，不要算作功能完成。

禁止在 Issue/截图上传个人成绩、密钥、学校原始资料和私有评测答案。

## 6. 队长每周怎么排

- 周初：核对上期结果，将本周目标拆成每人约 3 个有明确交接边界的交付任务，可继续拆成小 PR；负责人补实施步骤和依赖。
- 周中：至少一次全链路联调，优先解决 blocked、P0 和接口分歧。
- 周末：按实际证据完成验收，说明未完成原因，重新安排周次；不默默顺延。
- 后续周先保留大目标。下一期开始前细拆子任务；跨模块接口、数据样例、评测准备等前置依赖提前拆，不等临近才发现。

## 7. CI 和完成标准

现有 project-checks 校验契约/样例、基础披露/链接及已有模块的构建和测试；未实现模块会 SKIP。通过不等于全系统可用。

第一期建立组合启动、真实 HTTP 规划链路和浏览器冒烟检查；第二期扩充复杂分支与故障回归。工程检查可使用固定模型响应，但必须说明；真实模型另跑固定条件的评测与发布前验证。不得用模拟调用冒充真实模型已接通。

完整要求见[工程规范](16-engineering-and-debugging.md)、[公共契约](04-infrastructure-workflow.md)、[PR 模板](../.github/pull_request_template.md)。
