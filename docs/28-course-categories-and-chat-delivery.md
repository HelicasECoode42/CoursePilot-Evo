## 分类方案

分别保留三个维度：

1. 培养要求类别：决定学分计入哪一项，以学校或培养文件原类别和来源为依据。
2. 课程内容标签：例如人工智能、后端开发、数学基础、人文艺术，用于理解兴趣和课程相关性。
3. 目标学期开课信息：决定是否存在可选班次、教师和时间，以对应开课快照为依据。

同一门课程可以讨论多个兴趣方向，但不能因此重复计算学分。课程名称关键词匹配作为现有排序依据保留，不能标注为经 AI 完成的语义分类。后续模型可提出内容标签，标签须注明生成来源，不改变培养要求归属。

| 学校或培养文件类别 | 学生页面 | 推荐处理 |
| --- | --- | --- |
| 专业选修课 | 专业选修 | 第一阶段主推荐范围；结合缺口、已修、兴趣与评价 |
| 高年级研讨课 | 高年级研讨 | 使用现有少量课程资料提供课程层建议；开课资格与时间单独核验 |
| 通识课 | 通识选修，保留原分类名称 | 显示学校进度与已读取课程；候选目录缺失时不生成具体可选清单 |
| 任意选修课 | 任意选修 | 独立显示进度；是否可由其他类别抵扣，需要学校规则支持 |
| 公共基础课 | 学业记录中的公共基础 | 按用户决定退出本轮主动推荐；保留原记录，不删除课程事实 |
| 学科基础课、实践教学环节、新生研讨等 | 对应学业类别 | 保留进度；学生明确提出补修任务时另行处理，不混入默认选修推荐 |

“公共选修”可以作为页面导航名称，但不能自动等同于学校的通识课或任意选修课。若将二者放在同一导航入口，内部仍分别显示学校原类别与缺口。没有来源明确的抵扣规则时，选中一门课只能形成待规划选择，不能同时抵扣多个类别。

不按课程号前缀或兴趣推测培养类别。学校类别树按节点 ID 和父子关系保留；跨来源同名只显示参考对应，不自动提升为已确认抵扣关系。课程号冲突或学分不明确的记录保留待确认状态。

## 对话和画像的最小实现

学生输入问题后，Python 读取当前会话的培养快照、学校类别进度、学业记录和相关课程；只查询回答所需的评价。对话回答包含说明、课程引用、评价引用、一个必要追问或可确认的偏好修改。用户确认后，写入已有规划草稿，再经现有 Planning Runner 生成方案和 Java 核验。

对话建议的第一版操作为“记为兴趣方向”“加入待选课程”“优先考虑”“暂不采用”。对话回复不直接修改已修记录，也不自动替换已保存方案。前端保留完整引导入口，当前受到认可的其他页面不做整体重构。

画像第一版由事实引用和已确认偏好组成。事实保存记录 ID、快照 ID、来源与时间；偏好采用现有目标、优先级、兴趣文本、课程教师意愿和时间字段。AI 推断先作为待确认建议，不直接成为硬条件。会话草稿与跨会话长期档案分开描述；长期保存需要后续确定身份和读取方式，现有匿名会话不能自动认领其他会话记录。

规则负责已修排除、候选类别、已知学分计算、课程班次存在性、硬条件和时间冲突；AI 负责理解自由表达、追问、解释课程评价及提出发展方向。来源不足时仍可讨论方向，具体课程结论受已有事实约束。

## 推进顺序与验收

| 顺序 | 工作 | 需要完成的证据 |
| --- | --- | --- |
| 1 | 统一推荐范围和课程状态处理 | 公共基础退出主动推荐；专业选修、高年级研讨按明确范围取候选；已通过不重荐；在读、失败、未知分别处理；页面与 Runner 同一口径 |
| 2 | 补全对话事实输入与接口契约 | 对话读取学校报告缺口及其来源，保留本地 Audit UNKNOWN；接口区分回答、引用、追问与待确认修改；已有会话鉴权和预算复用 |
| 3 | 打通一轮真实聊天与确认 | 提问→回答→采用兴趣或课程→草稿更新；引用来自实际查询；没有评价能如实回答；本轮操作不自动生成或覆盖方案 |
| 4 | 完成聊天到规划的端到端流程 | 已确认偏好和选课进入现有规划请求；Java 返回核验；删除与换班使用现有确定性接口；模型错误保留草稿 |
| 5 | 增加多轮上下文与画像维护 | 后续提问保留已确认偏好；修改或取消选择可追踪；上下文截取不覆盖硬条件；会话过期处理明确 |
| 6 | 补公共选修目录与真实班次 | 取得对应来源后导入目录与分类映射，再验收通识/任意选修具体推荐；真实课表需目标学期班次来源 |
| 7 | 完成可靠性评测与交付 | 固定案例、独立预期、真实模型成功与失败记录；报告事实错误、已修重荐、引用正确性、确认操作、延迟和成本；在固定评测上推进受限策略改进 |

顺序 1 的现有差异是 Runner 排除所有非 FAILED 状态，而学分页按 PASSED 排除；顺序 2 的现有差异是 Runner 没有直接读取完整学校进度树。两项均已在接口核对文档记录，尚未因这份方案而自动修复。

现有基础包括学校导入、课程查询、评价查询、完整引导、方案生成、确定性删除换班、Java 核验及页面测试。尚未完成的是即时对话、确认动作接线、完整事实输入和跨会话画像。因此下一轮以“真实对话确认后能更新规划草稿”为交付范围，先完成一次完整往返，再增加多轮记忆和长期档案。

每个实施阶段保存代码 checkpoint 与测试结果。沿用 Luna 编写代码、主 Agent 维护文档和验收、完成一轮后另一名 Luna 独立审查的分工。接口变更同步 OpenAPI、Schema、提供者与消费者；测试中使用受控响应，真实模型验收单独记录调用次数与结果。

页面与接口现状见 [学生页面与数据流转](27-student-experience-and-data-flow.md)，上轮验收见 [学业资料与学分选课](checkpoints/records-credits.md)。
