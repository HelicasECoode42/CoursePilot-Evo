# CoursePilot：可解释的学业要求核对与选课规划助手

> 五人 Java 课程设计讨论稿 v0.1｜2026-09-29  
> 本文是拟议方案，不代表系统已开发、学校接口已接入或评测已有结果。附图中的 LearnAgent 是其他团队的方案示例，仅参考其“背景—目标—实现—分工”的表达方式。

## 一、项目定位

学生选课时要同时考虑培养方案、已修学分、课程类别、时间冲突和个人偏好。现有课表工具可以帮助查看课程和排除部分冲突，但学生仍需自己判断“还缺什么、哪些课程组合满足要求、为了空出一天需要牺牲什么”。本项目拟把这些判断变成可检查的计算过程，并通过对话让学生修改目标、比较方案。

**一句话目标：**学生输入已修课程和选课目标后，系统核对培养方案要求；在有班次数据的学期生成多套可行课表，说明每套方案满足的规则、牺牲的偏好以及数据来源；条件冲突时指出原因并支持重新规划。

本项目的主要技术问题是**带约束的决策与可解释的重规划**。Agent 负责理解目标、必要时澄清、调用核对和求解工具、与学生协商；Java 程序负责规则检查与组合计算。模型生成的文字不能替代规则计算结果。

## 二、用户场景与演示流程

一名学生导入或填写已修课程后提出：“本学期想补两门专业选修，数学课必须上，周五尽量空出来，别排得太碎。”

1. 系统按培养方案核对已完成与待完成的课程类别和学分，并展示规则依据。
2. Agent 把“数学课必须上”登记为硬条件，把“周五空着、少空档”登记为偏好；只有在含义影响结果时才追问。
3. 若已导入该学期班次与上课时间，Java 求解模块生成若干无时间冲突、满足硬条件的备选课表，并列出各项偏好的得失。
4. 若条件无解，界面显示导致无解的条件及可尝试的放宽方式；学生决定修改后再计算。
5. 推荐理由引用培养方案、班次快照或小本本的具体来源。开课、余量、成绩难度等未获得可靠数据的事项显示“未知”，不推测成确定事实。

**首版完成线：**能够在一份固定的学期数据快照上完成“要求核对→条件输入→生成方案或说明无解→修改条件后重算→展示依据”的闭环。页面保持简单，先证明决策结果可信。

## 三、数据来源与第一周可行性检查

| 数据 | 当前状态 | 首版使用方式 |
| --- | --- | --- |
| 培养方案 Excel | 团队成员称已有，具体字段和规则尚待检查 | 解析课程代码、类别、学分、必选关系等实际存在的字段；无法从表中确认的规则交由人工录入并注明来源 |
| 学生已修记录 | 由使用者提供 | 手动填写或导入模板；演示时用经同意的记录或虚构学生档案 |
| 学盟社选课小本本 PDF | 已有多期，评价为主观材料 | 人工核对后提取有限的课程评价标签，保留刊期、页码和原意；不将评价当作绩点或抢课概率 |
| 某学期开课班次与时间 | 尚未确认可持续获取 | 优先向校内项目维护者了解接口或取得可导入快照；历史快照只能演示对应学期，不能显示为本学期开课 |

**第 1 周决策点：**确认培养方案能否整理为规则，以及能否取得至少一份可核对的真实班次时间快照。若仅有培养方案，团队可以交付“毕业要求核对”模块，但应重新评估它是否足以支撑原定的选课规划和 Agent 展示目标，及时调整题目或范围。

项目使用导入和读取数据的方式；实际选课仍由学生在学校系统完成。学校页面脚本或其他项目的接口只作为待验证的数据线索，不在方案中预设其可用性。

## 四、功能与技术方案

### 4.1 Java 核心模块

| 模块 | 输入与输出 | 关键工作 |
| --- | --- | --- |
| 数据规范化 | Excel/录入表 → `Course`、`Offering`、`Requirement`、`CompletedCourse` | 统一课程代码、学分、类别、周次与节次；保存学期和数据来源 |
| 培养要求核对 | 已修记录 + 培养方案 → 已满足项、缺口、待确认项 | 按表中真实规则实现必修、类别学分或门数核对；不推断缺失的先修规则 |
| 方案求解 | 候选班次 + 硬条件 + 偏好 → 多套方案/无解结果 | 首版使用候选过滤、回溯与剪枝，再按预先定义的偏好评分排序；保存每项规则的检查结果 |
| Agent 交互 | 学生表达 + 当前状态 → 澄清、工具调用或方案解释 | 将目标转成结构化条件；调用核对、查课、求解、重算工具；解释必须来自工具返回的数据 |
| 会话与展示 | 方案、条件变更与来源 → 课表、差异和决策记录 | 学生能查看为何推荐、哪些条件未满足、改变条件前后发生什么 |

建议以 **Java 21 + Spring Boot** 实现数据、规则、求解、会话和 API；Excel 解析可用 Apache POI；持久化可按课程要求选 MySQL。前端做课表与方案对比即可。Agent 使用单个模型调用入口和有类型的 Java 工具，先完成可靠的工具闭环，再决定是否需要引入编排框架。若课程组合规模或约束复杂度超过自实现求解器能力，可参考 [Timefold 的 Java/Spring Boot 排课示例](https://docs.timefold.ai/timefold-solver/latest/quickstart/spring-boot/spring-boot-quickstart)调整求解实现。

### 4.2 条件边界

- **硬条件示例：**学生指定的必选课程、同一时间不可选两个班次、明确的最低课程类别要求。只启用已核实的规则。
- **软偏好示例：**周五空课、减少空档、偏好某位教师或某类课程；每项权重和得分可查看、可修改。
- **未知数据：**本期开课、席位、绩点倾向等若无来源，不能进入确定性评分。系统应保留待确认状态并说明它怎样影响推荐。
- **无解解释：**先通过逐项移除或放宽条件重新求解，找出实际阻碍可行方案的条件组合；向用户展示可行的替代选择，不由模型编造原因。

## 五、五人分工与集成约定

| 负责人 | 独立交付 | 与他人的接口 |
| --- | --- | --- |
| A：数据与来源 | Excel/班次导入、字段规范化、来源和学期标记 | 输出统一的课程、班次和培养规则对象 |
| B：培养规则 | 已修学分和类别核对、规则依据、缺失字段报告 | 提供 `auditRequirements` 结果给界面与 Agent |
| C：方案求解 | 冲突检查、候选过滤、偏好排序、无解分析 | 提供 `generatePlans`、`explainInfeasible`、`replan` |
| D：Agent 交互 | 条件提取、澄清、工具调用、解释生成 | 只通过 B/C 的工具接口获取事实与方案 |
| E：会话与展示 | Java 会话/API、课表与方案差异页面、演示数据入口 | 串联 A–D，保存条件变化和决策记录 |

每人负责自己模块的可运行交付和说明；场景样本、模块接口和最终演示由全组共同确认。建议在第 1 周先冻结 `Course`、`Offering`、`Requirement`、`Preference`、`PlanResult` 的字段，避免后期五份代码难以集成。成员姓名和具体负责范围在组内确认后填写。

## 六、八周安排与验收节点

| 周次 | 目标 | 当周可展示的成果 |
| --- | --- | --- |
| 第 1 周 | 核对 Excel 字段、班次数据来源、课程要求；确定演示用学期和规则 | 数据样例、统一对象、2–3 个用户任务；作出继续/缩范围决定 |
| 第 2 周 | 建立 Java 项目、导入和查询接口、最简课表页面 | 从真实快照读取课程与时间，能查看来源和学期 |
| 第 3 周 | 完成已修记录与培养要求核对 | 给出满足项、缺口和无法自动判断的规则 |
| 第 4 周 | 完成硬条件求解和方案展示 | 固定输入下生成可行课表，或明确返回无解 |
| 第 5 周 | 加入偏好评分、方案比较与修改后重算 | 同一学生目标下比较多套方案及得失 |
| 第 6 周 | 接入单 Agent 条件提取、澄清与工具调用 | 用自然语言完成一次完整的修改规划对话 |
| 第 7 周 | 固定案例评估和失败分析 | 保存每次输入、工具结果、方案、错误与耗时 |
| 第 8 周 | 修复主要问题、完成展示和报告 | 可复现演示、代码仓库、数据说明、评估报告 |

若第 4 周还没有可运行的确定性方案求解，先保证规则计算闭环，再压缩对话与界面工作；Agent 展示应以真实工具结果为基础。

## 七、评估方法与最终产出

全组在开发前准备约 **30–40 个固定任务**，覆盖正常选课、含糊偏好、条件冲突和数据缺失。任务数是工作量估计，最终以实际完成并人工核对的集合为准。评价至少记录：

1. **规则正确性：**培养要求核对与人工标注是否一致；生成方案有无违反硬条件。
2. **决策质量：**可行方案满足了哪些偏好；与固定规则或人工筛选基线相比有何差异。
3. **交互质量：**需要澄清时是否问对问题；无解解释是否对应真实冲突；缺数据时是否明确说明未知。
4. **使用成本：**完成一次规划的操作次数、耗时，以及模型调用次数或 Token（若能准确记录）。

预期交付包括：可运行 Java 服务和简洁网页、数据格式与来源说明、固定任务集、逐条决策记录、对照评估报告、项目演示。所有结果数字待运行后填写，报告保留失败案例。

## 八、与已有项目的区分及风险

- **与现有工具的关系：**[SHU 排课助手](https://github.com/shuosc/shu-scheduling-helper)已有查课和自动解冲突功能。本项目应在培养要求核对、偏好取舍和交互式解释上形成完整使用场景，避免只复刻课表展示。

最大风险是班次时间数据与培养规则的可获得性，其次是把主观课程评价误当成客观分数。第一周先核数据，第四周先核求解闭环，最后才以真实评估结果判断项目是否适合写进简历。10 月初开始投递时，本课程项目仍处于计划或开发阶段，不能写成已完成成果。
